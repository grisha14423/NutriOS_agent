# Health Coach Agent

Локальное Next.js-приложение с чатом для wellness-планов. Health Coach использует OpenRouter и выборочно читает профиль, дневник и рецепты через tools. Safety Reviewer оценивает план до его показа и сохранения. Чат показывает этапы работы и стримит одобренный план по частям.

Для вызовов модели используется OpenRouter Responses API. Health Coach работает через OpenAI Agents SDK, а Safety Reviewer сохраняет отдельный вызов `openai`.

Приложение не ставит диагнозы, не назначает лечение и не рекомендует лекарства.

## Настройка и запуск

Создайте `.env` в корне проекта и задайте параметры OpenRouter:

```env
OPENROUTER_API_KEY=ваш_ключ
OPENROUTER_MODEL=идентификатор_модели
# Необязательно: токен internal integration, которой открыт только раздел Wellness
NOTION_TOKEN=ваш_токен
SUPABASE_URL=https://ваш-проект.supabase.co
SUPABASE_SERVICE_ROLE_KEY=секретный_legacy_service_role_ключ
EMBEDDING_MODEL=openai/text-embedding-3-small
# Необязательно: отдельный ключ и OpenAI-compatible base URL для embeddings
EMBEDDING_API_KEY=ключ_сервиса_embeddings
EMBEDDING_BASE_URL=https://openrouter.ai/api/v1
```

Затем установите зависимости и запустите сервер разработки:

```powershell
npm install
npm run dev
```

Перед первым запуском RAG выполните по порядку SQL-файлы `docs/001_*.sql` - `docs/004_*.sql` в Supabase SQL Editor или DBeaver (либо примените эквивалентные миграции из `supabase/migrations/`). Уже выполненные миграции повторять не нужно. Затем запустите `npm run ingest`. Нужна embedding-модель с размерностью 1536; скрипт атомарно заменяет все секции из `knowledge/` без дублей. При смене `EMBEDDING_MODEL` повторите ingest: поиск отклоняет векторы, созданные другой моделью. Ключ `SUPABASE_SERVICE_ROLE_KEY` хранится только на сервере. Если `EMBEDDING_API_KEY` не задан, используется `OPENROUTER_API_KEY`; если `EMBEDDING_BASE_URL` не задан, используется OpenRouter.

## Memory vs RAG

`data/profile.md` и `data/log.md` - личная память о человеке и его текущих привычках. Коуч читает эти файлы через MCP tools только когда они нужны для задачи. Папка `knowledge/` - общая база знаний о рецептах, питании, тренировках и восстановлении. Команда `npm run ingest` превращает разделы Markdown в embeddings и сохраняет их в Supabase pgvector. Перед новым планом коуч вызывает `searchKnowledge` и получает наиболее близкие разделы с источниками; без успешного поиска новый план не сохраняется. Запрос и заголовки найденных разделов записываются в JSON-трейс, а число результатов видно в списке действий агента.

Откройте `http://localhost:3000`. Для production используйте `npm run build`, затем `npm run start`. Не запускайте production-сборку одновременно с сервером разработки: оба режима используют `.next`.

## До MCP / После MCP

До MCP чтение профиля, дневника и рецептов, а также запись плана подключались к коучу отдельными функциями в приложении. Для каждой новой интеграции приходилось вручную описывать tool и его вызов.

После MCP эти данные доступны через локальный stdio-сервер `src/mcp/markdownHealthServer.ts`: пять tools и четыре resources. Harness читает `src/mcp/servers.config.ts`, запускает включённые серверы на время запроса и передаёт их tools Health Coach через OpenAI Agents SDK. Новый сервер подключается записью в конфиге без правок harness и без обёрток над его tools. `suggestWorkoutTemplate` и `searchKnowledge` доступны коучу как локальные tools; `generateShoppingList` вызывается после одобрения плана. Harness сохраняет одобренный план через markdown-health. В UI и JSON-трейсе вызовы имеют источник `[markdown-health]`, `[filesystem]`, `[weather]`, `[notion]`, `[knowledge]` или `[local]`.

| Сервер | Пакет | Возможности | Авторизация |
| --- | --- | --- | --- |
| markdown-health | локальный `src/mcp/markdownHealthServer.ts` | Профиль, дневник, рецепты, сохранённый план | Нет |
| filesystem | `@modelcontextprotocol/server-filesystem@1.0.0` | Чтение и запись только в `data/` и `plans/` | Нет; разрешённые каталоги заданы при запуске |
| weather | `@cynosure-mcp/weather@1.0.5` | Прогноз Open-Meteo по городу или координатам | Нет API-ключа |
| notion | `@notionhq/notion-mcp-server@2.5.2` | Страницы Notion | `NOTION_TOKEN` internal integration; выключен без токена |

Промпт - просьба, конфиг - стена. Для filesystem серверу при запуске передаются только абсолютные пути `data/` и `plans/`, а промпт повторяет это ограничение. Не выдавайте доступ к корню проекта. Для Notion создайте internal integration, откройте ей только страницу или базу «Wellness» и запишите токен в `.env`. При отсутствии токена Notion не запускается. При наличии токена сервер включается автоматически. Права Notion integration ограничивают область записи независимо от просьбы в промпте. Weather только читает публичный прогноз, поэтому ему не нужны ограничения на запись.

Примеры задач: «Спланируй тренировку на завтра с учётом погоды», «Сохрани мой план ещё и в отдельный файл plans/<дата>.md» и, при настроенном Notion, «Сохрани план страницей в мой Notion». Для прогноза коуч читает город из `data/profile.md` и вызывает `get_weather_forecast`, который сам получает координаты через Open-Meteo. При неблагоприятной погоде предлагает зал или другую активность в помещении. Для Notion целевую страницу «Wellness» нужно открыть integration заранее.

Другие полезные MCP-серверы: Google Calendar, Database и Web Search. Здесь они не подключены. Google Calendar требует OAuth и вынесен за скобки этого примера.

Проверьте tools и resources каждого включённого MCP-сервера командой `npm run mcp:inspect`. Отключённые серверы показываются без списка tools.

## Как работает приложение

1. Отправьте сообщение в чате через поле внизу страницы клавишей Enter или кнопкой. Shift+Enter добавляет новую строку; поле растёт вместе с текстом до заданной высоты. Например: «Составь план питания на завтра с учётом моего профиля и дневника за последние два дня. Добавь лёгкую тренировку». Пока агент работает, ввод и кнопка «Новая сессия» недоступны. После завершения кнопка очищает единственный чат. История нигде не сохраняется и также исчезает при обновлении страницы.
2. Health Coach решает, какие данные запросить. MCP предоставляет `read_profile`, `read_recent_logs` и `list_recipes`, а локальный tool `suggestWorkoutTemplate` предлагает тренировку.
3. Safety Reviewer получает только текст плана и возвращает вердикт, оценку от 0 до 10 и замечания. У reviewer-а нет tools.
4. При `revise` замечания возвращаются коучу вместе с историей его вызовов tools. Harness допускает до трёх раундов. Если reviewer одобрил план с оценкой ниже 7, harness просит коуча доработать его.
5. При `approve` и оценке не ниже 7 harness сохраняет проверенный план в `data/output.md`. Если задача включает список покупок, он создаётся в `data/shopping.md` из одобренного плана.
6. Вердикт `needs_human_professional` останавливает выдачу плана.

Чтобы использовать уже сохранённый план для покупок, попросите составить список к готовому плану, например: «Составь список покупок к сохранённому плану». Если сохранённого плана нет, приложение сообщит об этом. Для нового плана и покупок укажите оба действия, например: «Составь новый план питания на завтра и список покупок к нему».

Во время выполнения в чате обновляется таймлайн: чтение профиля, поиск знаний с текстом запроса, создание плана, проверка безопасности и, если нужно, доработка по раундам. Каждый tool call показан отдельной строкой со своей иконкой и источником `[mcp]`, `[local]` или `[rag]`; активные этапы и инструменты мигают. После одобрения план появляется по частям с форматированием Markdown; под ним указаны вердикт и оценка. При `needs_human_professional` вместо плана показывается карточка «Требуется специалист» с замечаниями. При ошибке остаются завершённые этапы и действия tools, индикаторы незавершённых действий исчезают. В серверный журнал не записываются содержимое профиля и дневника.

## Как дебажить агента

Каждый запуск сохраняет JSON-трейс в `runs/`: задачу, модель, версии промптов, оценки по раундам и вызовы tools. При ошибке трейс содержит `verdict: "error"`, сообщение ошибки и уже собранные данные. Каталог исключён из git. Пример формата: `run-example.json`.

После изменения промпта или модели повторите задачу из трейса и сравните результаты, включая название модели:

```powershell
npm run replay runs/run-XXX.json
```

Чтобы последовательно проверить шесть задач, включая раннюю остановку медицинского запроса, решение reviewer-а по медицинскому риску, вызовы tools для списка покупок и поиск рецепта в базе знаний, запустите:

```powershell
npm run eval
```

Скрипты читают параметры OpenRouter из `.env`. Replay и eval запускают агента заново; одобренный план может обновить `data/output.md`.

## Данные и основные файлы

- `data/profile.md` и `data/log.md`: личные данные, которые коуч читает только по запросу через tools.
- `data/recipes.md`: любимые рецепты, доступные коучу.
- `data/output.md`: последний одобренный план.
- `data/shopping.md`: последний список покупок.
- `prompts/`: версии инструкций Health Coach и Safety Reviewer.
- `src/mcp/markdownHealthServer.ts`: stdio-сервер для Markdown-данных.
- `src/mcp/servers.config.ts`: список MCP-серверов, команды запуска и флаги включения.
- `plans/`: отдельные файлы планов, созданные по запросу через filesystem MCP.
- `src/skills/`: локальные tools для шаблона тренировки и списка покупок. Старые функции доступа к данным сохранены в файлах с суффиксом `-UNUSED.ts` и не вызываются.
- `src/harness/`: раунды проверки, порог безопасности и оркестрация вызовов.
- `app/api/chat/route.ts`: потоковый endpoint `POST /api/chat` для одного сообщения чата; отправляет data-события этапов и tools, затем части одобренного плана.
- `app/api/agent/run/route.ts`: серверный endpoint `POST /api/agent/run`, принимает JSON `{ "task": "..." }`.

Профиль, дневник, сохранённый план, отдельные планы и список покупок исключены из git.
